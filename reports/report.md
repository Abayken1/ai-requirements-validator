#### Т-01 · без номера · Часть A / Цели

> Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.

**Д-01 · Однозначность · существенно**

- Проблема: Термин «личный бюджет» не определён и не совпадает с термином «порог» из Ф-1 и Ф-3. Неясно, является ли бюджет синонимом порога или отдельной сущностью.
- Место: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Исправить: Заменить «личного бюджета» на «установленного порога расходов» или добавить в глоссарий определение: «Личный бюджет — это порог расходов, заданный клиентом».

**Д-02 · Проверяемость · существенно**

- Проблема: Формулировка цели не позволяет составить тест-кейс с чётким pass/fail: нет критерия «узнал/не узнал», нет канала доставки, нет времени реакции.
- Место: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Исправить: Сформулировать как проверяемое требование: «Система должна отправлять push-уведомление в течение 1 минуты после проведения покупки, в результате которой сумма расходов за месяц достигла или превысила заданный порог» (см. Ф-3, NFR).

**Д-03 · Полнота · незначительно**

- Проблема: Цель не содержит измеримых критериев успеха (какие каналы, какой SLA, что считается «узнать»). Нельзя использовать как основу для приёмки без ссылки на Ф-3.
- Место: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Исправить: Добавить ссылку на функциональные требования Ф-3 и нефункциональные (SLA push в течение минуты) или перенести в раздел контекста, оставив только в Ф-3 проверяемые критерии.

**Д-04 · Корректность · незначительно**

- Проблема: Противоречие терминологии: цель говорит о «бюджете», Ф-1/Ф-3 — о «пороге». В критериях приёмки проверяется именно порог.
- Место: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Исправить: Унифицировать термин: везде использовать «порог расходов» (threshold).

**Д-05 · Соответствие · незначительно**

- Проблема: Требование не имеет уникального идентификатора в документе (назначен Т-01 только для ревью). Шаблон подразумевает нумерацию требований.
- Место: «Цели»
- Исправить: Назначить идентификатор, например, Ц-01 или BR-01, и добавить в таблицу требований.

#### Т-02 · без номера · Часть A / Архитектура решения

> Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.

**Д-06 · Уместность · существенно**

- Проблема: Архитектурное решение (конкретные сервисы и их связи) зафиксировано как требование. Это ограничивает проектирование: названия сервисов («учёт расходов», «сервис push») — это детали реализации (HOW), а не бизнес-потребность (WHAT).
- Место: «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push»
- Исправить: Перенести в раздел «Архитектура решения» как информативную схему, а не требование. В требованиях оставить только внешние интерфейсы: «Приложение управляет настройками через API настроек. Процессинг передаёт события покупок в систему учёта расходов, инициирующую push».

**Д-07 · Корректность · незначительно**

- Проблема: Название компонента «учёт расходов» не совпадает с Sequence Diagram («сервис расходов») и REST API («AlertsController»/хранилище настроек). Несоответствие терминологии внутри документа.
- Место: «Карточный процессинг → учёт расходов → сервис push»
- Исправить: Унифицировать название: везде использовать «Сервис расходов» (Expense Service).

**Д-08 · Соответствие · незначительно**

- Проблема: Отсутствует идентификатор требования/раздела.
- Место: «Архитектура решения»
- Исправить: Добавить идентификатор, например, AR-01.

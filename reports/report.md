#### Т-02 · без номера · Часть A / Архитектура решения

> Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.

**Д-02 · Уместность · существенно**

- Проблема: Описывает архитектурное решение (КАК), а не бизнес-потребность (ЧТО). Содержит конкретные компоненты: сервис настроек, учёт расходов, сервис push.
- Место: «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.»
- Исправить: Убрать из функциональных требований; оставить в разделе архитектуры как информационное описание, либо сформулировать как ограничение: «Система должна обеспечивать взаимодействие мобильного приложения с сервисом настроек и процессинга с сервисом push».

**Д-03 · Однозначность · существенно**

- Проблема: Стрелки «→» не определены: вызов API, асинхронное сообщение, синхронный запрос? Не ясно, кто инициирует.
- Место: «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.»
- Исправить: Уточнить тип взаимодействия в архитектурном разделе (например, REST, Kafka).

**Д-04 · Полнота · существенно**

- Проблема: Отсутствуют условия, ошибки, таймауты, повторные попытки, формат данных.
- Место: «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.»
- Исправить: Добавить в архитектурное описание нефункциональные требования к интеграции (протоколы, SLA, обработка ошибок).

**Д-05 · Проверяемость · существенно**

- Проблема: Нельзя проверить тестом: нет критериев успеха, нет ожидаемого поведения.
- Место: «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.»
- Исправить: Перенести в архитектуру, а проверяемые требования вынести в Ф-1..Ф-4.

**Д-06 · Единичность · незначительно**

- Проблема: Два независимых потока в одном предложении: настройка порога и обработка покупки.
- Место: «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.»
- Исправить: Разделить на два архитектурных утверждения или требования.

**Д-07 · Соответствие · незначительно**

- Проблема: Нет идентификатора, находится в разделе «Архитектура решения», а не в требованиях.
- Место: «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.»
- Исправить: Добавить идентификатор (например, АРХ-1) и оформить как архитектурное ограничение.

- **Н-02** (Т-14, Т-19, Т-20, Т-21, Т-22, Т-23, Т-24, Т-25, Т-26, Т-27, Т-28, Т-29, Т-30): Эндпоинт назван saveLimit, описан как «чтение порога», но реализует запись (замену настройки) и использует GET — небезопасный метод для изменения состояния. В части A (Т-14, Sequence Diagram) требуется чтение порога, но эндпоинта чтения нет.
- **Н-03** (Т-31, Т-32, Т-33, Т-34, Т-35, Т-36, Т-37, Т-38, Т-39, Т-40): HTTP 200 возвращается и при бизнес-успехе (result=OK), и при бизнес-ошибке (result=ERROR) — разная структура ответа. Коды 400/401/404 не содержат поле result. Клиент не может единообразно парсить ответ.

*Неполные формулировки и пропуски*

- **Н-11** (Т-01, Т-07, Т-08, Т-09, Т-10): Критерии приёмки покрывают только 3 позитивных сценария. Отсутствуют: граничные значения (1 000, 1 000 000), выключенный переключатель, возврат, переводы/снятие, смена порога вверх/вниз, включение/выключение уведомления, повторная покупка в том же месяце (макс 1 push), смена карты, ошибки процессинга/пуша, идемпотентность события процессинга.
- **Н-12** (Т-13, Т-07, Т-28): Противоречие единиц измерения: в требованиях к данным сумма покупки в тиынах (1/100 тенге), а порог и API-параметр amount — в целых тенге. Это приведёт к ошибкам расчёта и сравнения.
- **Н-13** (Т-12): Нефункциональные требования неполны: отсутствуют безопасность (шифрование, аудит, rate limiting), доступность (SLA, отказоустойчивость), нагрузка (RPS, пики), мониторинг/логирование, защита персональных данных (PII: последние 4 цифры карты), хранение и ретеншн.

*Другие критичные*

- **Н-14** (Т-01, Т-07, Т-08, Т-09, Т-10, Т-16, Т-17, Т-18): Нет трассируемости цели к требованиям и к критериям приёмки. Приёмка не проверяет Ф-2 (возврат, исключения), Ф-3 (макс 1 push/месяц), Ф-4 (смена порога), не проверяет цель «в момент покупки» (latency). Невозможно доказать, что набор решает бизнес-цель.
- **Н-15** (Т-07, Т-08, Т-09, Т-10, Т-14, Т-19, Т-20, Т-21, Т-22, Т-23, Т-27, Т-28, Т-29): В исходном документе нет идентификаторов требований (добавлены нарезчиком). Нет ссылок между Частью A и Частью B: не указано, какие параметры API реализуют Ф-1..Ф-4. Сложно отследить изменения и покрытие.

## 6. Итог

### Можно ли начинать разработку и тестирование: Нет

Правило: в документе есть критичные дефекты — до их исправления разработку и тестирование начинать нельзя.

Документ содержит 40 требований с 106 нарушениями, из которых 14 критичных. Главные риски: противоречия между критериями приёмки и бизнес-правилами (даты, лимиты пушей), некорректный дизайн API (GET для записи, смешанные коды 200), несоответствие единиц измерения (тины/тенге), отсутствие нефункциональных требований и трассируемости целей. Разработку и тестирование начинать нельзя до устранения всех критичных дефектов.

**Что исправить в первую очередь:**

1. Н-01, Д-30, Д-60: Исправить логику определения месяца — использовать дату совершения покупки (Ф-2), а не дату проведения, во всех критериях приёмки и тестах.
2. Н-02: Перепроектировать эндпоинт saveLimit — разделить на GET /limit (чтение) и POST/PUT /limit (запись), убрать изменение состояния через GET.
3. Н-03: Унифицировать HTTP-ответы — возвращать 2xx только при бизнес-успехе (result=OK), 4xx/5xx при ошибках с единой структурой ошибки, убрать result=ERROR в теле 200.
4. Н-12: Привести все денежные величины к единой единице (рекомендуется тины) в требованиях, API (amount), модели данных и валидации.
5. Н-14: Ввести матрицу трассируемости: цель → Ф-1..Ф-4 → требования (Т-01..Т-40) → критерии приёмки/тест-кейсы, обеспечить покрытие всех бизнес-правил и нефункциональных целей.

## Приложение. Методика

- Нарезчик выделяет требования; код проверяет, что цитата каждого требования есть в документе, и добавляет пронумерованные требования, если модель их пропустила.
- Ревьюер проверяет требования пачками по критериям ниже, в контексте всего документа. Два ревьюера набора отдельно ищут противоречия и пропуски.
- Каждое замечание должно цитировать документ. Код ищет цитату в тексте; если не нашёл — замечание считается неподтверждённым и не входит в сводку и итог.
- Решение «можно ли начинать» принимает код по правилу: есть критичные дефекты — «Нет»; только существенные — «С оговорками»; иначе — «Да».
